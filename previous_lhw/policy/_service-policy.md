## 1. 서비스 개요 (Why)

관리업체가 **다수의 건물**에 대한 관리비·공과금(전기·수도·가스)·고지서 발행·수납·미납·민원(AS)·이사정산 업무를 처리하는 **멀티테넌트 SaaS**. 기존 로컬 전산(설치형)을 대체하며, 사무실 PC(직원)·현장 모바일(현장관리자)·입주민 앱(카카오)까지 하나의 데이터로 연결한다.

- 핵심 가치: 건물·세대 단위 관리비 산정 자동화, 공과금 검침→부과→발행→수납의 일원화, 현장/입주민까지 실시간 연동.
- 소스코드 전체 소유권·저작권은 발주사에 귀속(기능정의서 P-5).

## 2. 롤 & 권한 모델

### 2.1 롤 정의

| 롤 | 표면(Surface) | 사용자 | 핵심 역할 |
|----|------|--------|-----------|
| **admin** | 본사 웹(HQ) | SaaS 운영사(본사) 관리자 | 관리업체(테넌트) 계정·사용량·포인트·정산 관리, 전체 서비스 운영 |
| **staff** | 사무실 PC (ERP) | 관리업체 직원 | 건물·입주자 등록, 관리비/공과금 셋팅·부과, 고지서 발행, 수납·미납·민원·이사정산 등 핵심 업무 |
| **partner** | 모바일 웹(반응형) | 관리업체 소속 **현장관리자** | 현장 검침(지침 입력)·AS 접수/처리·이사정산 현장 입력, 조회 |
| **resident** | 카카오 기반 앱/웹 | 입주민(세입자) | 관리비 확인·상세, 우리건물 공지 확인, 퇴실 신청, 카카오/스마트 고지서 신청, 본인인증 |

> `partner`(현장관리자)는 관리업체 소속이며, staff 화면의 **협력업체 관리(`vendor-management`)** 에서 다루는 외부 협력업체(CCTV·승강기·소방·청소 등)와는 **다른 개념**이다. 협력업체는 로그인 롤이 아니라 staff가 관리하는 데이터 대상이다.

### 2.2 멀티테넌트 & 데이터 격리 (기능정의서 P-1, P-2)

- **테넌트 = 관리업체.** 관리업체별 데이터는 완전히 분리된다. 한 테넌트의 사용자는 다른 테넌트 데이터에 접근 불가.
- `admin`(본사)은 테넌트를 넘나드는 운영 권한을 가지되, **운영 메타데이터(계정·사용량·과금·포인트)만 열람**한다. 개별 테넌트의 업무 데이터(건물·입주자·관리비 내역 등)에는 접근하지 않는다 — 데이터 격리 원칙 유지.
- **사무 관리자(staff) · 현장 관리자(partner) · 세입자(resident)는 서로 완전히 다른 화면(표면)을 사용**한다. 롤별 접근 권한은 2.3 참조.

### 2.3 롤별 접근 권한

권한 모델은 롤마다 성격이 다르다 — staff는 **메뉴 단위로 자유 설정**, partner는 **고정 기능 세트**, resident는 **본인 세대 한정**이다.

**staff (사무 관리자) — LNB 항목별 개별 설정형**
- 고정 등급이 아니라, **계정별로 LNB 메뉴 항목 단위 접근권한을 자유롭게 부여/제한**한다. (예: A직원은 '수납·민원'만, B직원은 '관리비 부과 셋팅'까지 접근)
- 직원 계정 등록·관리 및 담당자(관리·검침·청소) 지정은 `staff/staff-management`(계정·직원)에서 수행(기능정의서 I-5, A-9). 담당자별 필터링·엑셀 다운 지원.
- LNB 항목별 권한은 **테넌트 최고관리자(계정 유형: `마스터`)** 가 '계정·직원'(`staff-management`) 화면에서 각 직원에게 부여/제한한다. `마스터`는 테넌트 내 최상위 계정으로 직원 계정·권한을 관리한다. (설정 화면은 고도화 후 구현.)

**partner (현장 관리자) — 고정 기능 세트**
현장관리자 계정이 수행 가능한 기능(고정):
- 이사정산 입력
- 검침(지침) 입력
- 수납 **조회** (조작 불가)
- 건물 정보 **열람**
- 세입자 정보 **열람**
- **본인에게 할당된** A/S 현황 조회 및 A/S 등록

  → partner의 수납·건물·세입자는 모두 **읽기 전용**이며, 쓰기 가능한 것은 이사정산·검침·본인 A/S뿐이다.
- 위 목록이 **전부**다. 문자·알림톡 발송, 공지 확인 등 그 외 기능은 **불가** (현장관리자는 고정 기능 세트만).

**resident (세입자) — 본인 세대 한정**
- 본인 세대 관리비 확인·상세, 우리건물 공지, 퇴실 신청, 카카오/스마트 고지서 신청 (4.4 참조).

**admin (본사) — 운영 권한** (2.2 참조).

| **이사정산** | 퇴실 시 사용일까지 관리비·공과금 정산. 중도퇴실/공실처리 분기 |
| **민원 / AS접수** | 입주민 요청 접수·처리. 미결·완결·보류·반복 상태 |
| **고객번호** | 공과금 납부자 번호(수도 세대당 2개, 전기 층별 지원) |

| **단수(端數)** | 고지 금액의 끝자리 절사/표기. 단수표기·단수해지 설정 |
| **공실 / 중도퇴실** | 세대 비어있음 / 계약기간 중 퇴실. 정산·수납 처리 분기 |

## 4. 표면(Surface) 구성

### 4.1 admin — 본사 웹(HQ)
화면(폴더): `overview`(개요) · `tenants`/`tenant-detail`(관리업체) · `accounts`(계정) · `usage`(사용량) · `points`(포인트) · `settings`(설정) · `login`
- 성격: 플랫폼 운영. 테넌트(관리업체) 온보딩·과금·사용량 모니터링.
- **포인트(선불 잔액) 기반 과금**: 테넌트가 외부(결제) 서비스에서 충전한 금액을 `points`로 기록하고, 이 잔액을 기준으로 전체 서비스 이용을 관리한다. **잔액이 0이 되면 해당 테넌트의 서비스 이용을 하드 스톱**(전체 중단)한다.
- **차감·계측**: 포인트는 **문자·알림톡·팩스 발송 건수**에 따라 차감된다. `usage`(사용량)는 이 발송 건수를 계측한다.

### 4.2 staff — 사무실 PC ERP
LNB 구조(고도화 화면 기준):
- **관리업무**: 건물·입주자 → 공과금 관리(고객번호조회·전기·수도·가스) → 관리비 부과 셋팅 → 항목등록관리 → 서류 발행·출력 → 수납·민원 → 미납관리 → 이사정산 → 협력업체 관리 → 문자·알림톡
- **설정(LNB 하단)**: 계정·직원 · 셋업 설정
- 그 외 화면: 건물/입주민 등록·상세, 장기수선(`long-term-repair`), 공지관리(`notice-management`), 이사정산 세부(`moving-elec/gas/water/status`) 등
- moving-settlement·messaging·staff-management·setup은 **고도화 전**이며, 세부 정책은 각 화면 고도화 완료 후 해당 화면 PRD에서 확정한다. (staff 대시보드 화면은 없음. 수납처리·자동이체는 `receipt-management`로 통합.)

### 4.3 partner — 현장 모바일 웹
화면(폴더): `mobile-home` · `mobile-login` · `mobile-profile` · `mobile-building` · `mobile-tenant` · `mobile-meter`(검침) · `mobile-as`/`mobile-as-new`(AS) · `mobile-ms-new`(이사정산) · `mobile-inquiry`
- 성격: 현장에서 마우스 없이 즉시 입력. 검침 시 전월대비 급증·급감 경고, 최근 3개월 이력·입주날짜 표시(기능정의서 J-2~J-4).
- 권한 제한: 이사정산 입력은 "정산금계산+저장" 버튼만 사용 가능(M-1). AS는 본인/건물별 현황 조회(K-3).

### 4.4 resident — 세입자 앱(카카오 기반)
화면(폴더): `resident-login`/`resident-auth`/`resident-verify`(인증) · `resident-home` · `resident-bill`/`resident-bill-detail`(관리비) · `resident-notice`/`resident-notice-detail`(공지) · `resident-notify` · `resident-me` · `resident-pending`/`resident-nomatch` · `resident-terms`/`resident-privacy`
- 카카오 로그인 기반(관리비확인·퇴실신청·카카오고지서신청 등은 로그인 필요, N-1).
- **관리비 상세는 로그인 없이 링크로 열람 가능**(고령자·접근성 배려). 링크 유효기간 **1년**, 계좌·금액 복사 기능(O-2).
- 공지 알림톡의 [공지확인하기] → 세입자 웹 우리건물 공지로 연결(신규·중요·긴급 템플릿 구분, N-2).

## 5. 공통 UI·인터랙션 규칙

세부 시각 규칙은 `CLAUDE.md`가 정본이며, 여기서는 정책 차원만 요약한다.

- **셀렉터(드롭다운)**: 네이티브 `<select>` 금지, 커스텀 드롭다운 사용. 닫힌 버튼 + 열린 목록 모두 디자인 시스템 적용(기준: `staff/utility-water`의 `.uc-dd`). (CLAUDE.md)
- **모달 버튼**: height 40 · radius 11 · font 13.5 · weight 700. (CLAUDE.md)
- **색상**: Primary 남용 금지. **음수(감액·차액·증감)는 빨간색**, 양수는 별도 색 없음. (CLAUDE.md)
- **날짜 입력**: 전 화면 **달력 방식으로 통일**(직접 타이핑 대신 마우스), 기능정의서 Q-4. 이사정산 입금일 등은 달력 버튼으로만 입력(H-5).
- **건물명 자동완성 & 유지**: 페이지 이동 시 선택한 건물명 유지, 마우스만으로 검색(Q-3).
- **출력물 워터마크**: 회사명 워터마크 출력(I-6, D-7).
- **표면별 독립 구현**: staff(PC)와 partner(모바일)는 화면을 별개로 구현하며, **디자인 토큰·공통 UI 규칙(`CLAUDE.md`)만 공유**한다. 컴포넌트 코드 공유는 강제하지 않는다.

## 6. 공통 화면 상태

각 화면 PRD는 아래 상태를 기본 점검한다. 서비스 공통 기본값:

| 상태 | 공통 표준 |
|------|-----------|
| 빈(Empty) | 목록·영역에 데이터가 없으면 "OO이(가) 없습니다" 안내 문구 노출. 생성 가능한 영역은 생성 유도 액션(버튼)을 함께 표시 |
| 로딩 | 데이터 요청 중 로딩 표시(목록·표는 스켈레톤, 개별 액션은 인라인 로딩)를 노출하고, 완료 전 중복 조작을 막는다 |
| 성공 | 처리 결과를 토스트로 알린다("발행되었습니다","수납 처리되었습니다" 등, 기존 staff 패턴 유지) |
| 없음(No result) | 조회 결과 없음 시 "검색 결과가 없습니다" 안내 |
| 제한(권한) | 권한 없는 **LNB 메뉴는 숨김**, 화면 내 권한 없는 **액션(버튼)은 비활성(disabled)** 처리 |
| 에러 | 외부연동(문자·은행·카카오 등) 실패 시 사용자에게 실패 사유를 알리고 재시도를 안내한다. 실패해도 원본 데이터는 훼손하지 않는다 |

## 8. 보안 · 감사

- **권한 제어**: 롤·등급별 접근 제어(P-2). 상세는 2절.
- **감사 로그**: 주요 데이터 변경 이력을 시스템이 **뒤에서 자동으로 기록·저장**한다(P-3). 사용자용 **로그 조회 화면은 두지 않는다**(백엔드 기록 전용).
  - **기록 범위 = 주요 데이터 전반.** 금전 관련(부과 확정·수납·수납취소·이사정산·연체) + 건물·입주자 정보 + 관리비 셋팅 + 계정·권한 변경의 **생성·수정·삭제**를 기록한다. (단순 조회·로그인은 제외.)
  - 기록 항목(권장): 행위자(누가)·시각(언제)·대상(무엇을)·변경 전/후 값·테넌트.
- **개인정보 보유·파기**: resident 약관·개인정보 화면 존재(`resident-terms`, `resident-privacy`).
  - **무기한 보관하지 않는다.** 입주자 개인정보(연락처·계좌·차량번호·**전출정보** 등)는 계약 종료·정산 완료로 수집 목적이 끝나면 정해진 보유기간 뒤 **파기**한다(개인정보보호법 제21조 취지).
  - **예외**: 법령상 보존 의무가 있는 정산·과세 관련 기록은 해당 **법정 기간 동안 분리 보관** 후 파기하며, 보존 목적 외 사용하지 않는다.
  - **보유기간(잠정): 계약 종료 후 5년.** 정산·과세 관련 법정 보존기간(통상 5년)에 맞춘 값이며, 이후 파기한다. 최종 기간·법정 보존 항목은 법무 검토로 확정한다.
- **데이터 소유권**: 소스코드·데이터 소유권 발주사 귀속(P-5).

## 9. 전체 업무 플로우 (기본 흐름)

```
[건물 등록] → [입주자 등록] → [검침/지침 입력(현장 or 사무실)]
   → [관리비 부과 셋팅] → [부과 확정] → [고지서 발행/발송(지로·A4·카톡·팩스)]
   → [수납(수동/자동이체/은행매칭)] → [미납관리(연체·독촉·단전단수예고)]
   → [퇴실 시 이사정산(중도퇴실/공실처리 분기)]
```

- 현장(partner)은 검침·AS·이사정산 입력 지점에서 흐름에 합류.
- 입주민(resident)은 고지서 수신·관리비 확인·공지·퇴실신청 지점에서 합류.
- 각 단계의 상태 전이(예: 부과 확정 후 수정 가능 여부, 발행 후 재발행 규칙)는 **해당 화면 PRD에서 확정**한다(공통 정책에서는 흐름만 정의).

## 10. 결정 로그 & 스코프

**서비스 공통 정책에 미정 항목은 없다.** 아래는 미정이 아니라, **의도적으로 각 화면 PRD 단계로 넘긴** 사항이다.

- **각 화면의 상태 전이 세부**(부과 확정 후 수정/재발행 등) → 해당 화면 PRD에서 정의(공통은 흐름·상태 표준만 제공).
- **고도화 전 4개 화면**(moving-settlement·messaging·staff-management·setup)의 세부 정책 → 각 화면 고도화 완료 후 해당 화면 PRD에서 정의.

**운영 확인 필요(정책값은 확정)**
- 개인정보 보유기간: 현 정책값 **계약종료 후 5년**. 최종 기간·법정 보존 항목은 법무 검토로 확인(정책 공백 아님).
