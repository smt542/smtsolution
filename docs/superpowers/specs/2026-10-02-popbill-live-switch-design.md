# 팝빌 실발송 운영 전환 설계

- 작성: 2026-10-02
- 범위: 문자(SMS·LMS)·팩스를 팝빌 운영 환경으로 실발송하기 위한 안전장치·보완·전환 절차. 알림톡은 카카오 채널 승인 뒤 별도로 연다.
- WBS: 주택관리ERP › 사무실 관리자_문자·알림톡 관리
- 관련 문서: `docs/ops/popbill-delivery.md`, `docs/ops/eventbridge-scheduled-messaging.md`, `docs/superpowers/specs/2026-09-03-per-org-sender-number-design.md`, `docs/superpowers/specs/2026-09-09-messenger-fab-design.md`

## 1. 목표와 성공 기준

목표: 출시 전에 관리비서에서 보낸 문자가 실제 휴대폰에 도착하는 상태를 만든다.

성공 기준:

1. 배포본에서 보낸 SMS 1건·LMS 1건이 담당자 휴대폰에 도착한다.
2. 몇 분 안에 발송 결과가 '완료'로 바뀌고, 조직 포인트가 플랫폼 설정 단가만큼 차감된다.
3. 허용 목록 밖 번호로 보낸 건은 팝빌로 나가지 않고 '발송 제한 번호'로 실패하며, 포인트가 차감되지 않는다.
4. 매월 반복 예약이 운영 결과 확정 뒤 다음 달 회차를 1건 만든다.

## 2. 현재 상태 (2026-10-02 확인)

### 코드

- 문자·LMS·알림톡·팩스는 모두 팝빌을 거친다(`lib/popbill/*`). 진입점: 즉시 발송 `app/api/messaging/send`, 예약 워커 `app/api/messaging/dispatch-scheduled`(EventBridge 1분), 팩스 `app/api/bill/fax/send`, 결과 재조회 `app/api/delivery/reconcile`.
- `POPBILL_IS_TEST`는 SDK `IsTest`로 그대로 넘어간다(`lib/popbill/sdk.ts`). 운영 전환에 필요한 코드 분기는 없다.
- 결과 정규화(`lib/popbill/results.ts`): 문자는 state=3·result=100만 성공, state<3은 대기, 그 밖은 실패. 팝빌 문서의 상태코드(0 접수·1 대기·2 처리·3 완료·4 취소)·결과코드(100 성공)와 일치한다.

### 팝빌 조회 결과

같은 LinkID `SMTSOLUTION`·사업자번호 5428103683으로 조회 API만 호출했다(발송·과금 없음).

| 항목 | 테스트 환경 | 운영 환경 |
|---|---|---|
| 연동회원 | 가입 | 미가입 |
| 잔액 | 0 (파트너 잔액 1,500) | `-99010016 사용할 수 없는 서비스입니다.` |
| 문자 발신번호 | 0426328770 승인(state 1) | 조회 불가(-99010016) |
| 팩스 발신번호 | 0426236642 승인(state 1) | 조회 불가(-99010016) |
| 문자 단가 | 12원 | 조회 불가(-99010016) |

팝빌 문서: "팝빌 테스트 환경과 운영 환경은 독립적인 시스템으로 구성되어 운영전환시 데이터 이관 또는 공유가 불가합니다." 운영 환경의 회원·발신번호·포인트는 새로 준비해야 한다.

### 배선·데이터

- 로컬(`.env.local`)과 배포본(Amplify)은 같은 Supabase 프로젝트와 같은 팝빌 테스트 키를 쓴다(2026-09-22 확인).
- 결과 재조회 크론은 `docs/ops/eventbridge-scheduled-messaging.md` 7절에 배선 방법만 있고 배선 기록이 없다. AWS SSO 만료로 실제 규칙은 확인하지 못했다.
- 수신번호로 실발송을 막는 장치는 없다. 있는 상한: 즉시 발송 5,000명, 팩스 500건, 예약 워커 1회 50건.

## 4. 설계

### 4.1 실발송 허용 번호 목록

환경변수(서버 전용):

- `POPBILL_LIVE_ALLOWLIST`: 쉼표로 구분한 번호 목록. 항목마다 숫자만 남겨 비교한다(하이픈·공백 무시). `*` 항목은 전체 허용.
- `POPBILL_LIVE_RESTRICTED_ORG_IDS`: 쉼표로 구분한 조직 id. 이 조직은 `*`를 무시하고 목록에 적힌 번호로만 보낸다.

규칙:

- `POPBILL_IS_TEST=false`일 때만 적용한다. 테스트 모드는 지금과 같다.
- 수신번호(SMS·LMS·알림톡은 휴대폰, 팩스는 팩스번호)를 숫자만 남겨 목록 항목과 정확히 비교한다.
- 환경변수가 없거나 비어 있으면 전부 차단한다.
- 두 설정 중 하나라도 형식이 틀리면(허용 번호는 `*` 또는 숫자·하이픈·공백으로 된 8~12자리, 조직 id는 양의 정수 — `;`·공백 구분, `+82`, 따옴표 등) 운영 모드에서 전부 차단하고 서버 로그에 한 번 남긴다. 데모 조직 제한이 형식 오류로 조용히 꺼지지 않게 한다(2026-10-02 리뷰 반영).
- 판정은 함수 하나로 한다: 조직 id·수신번호·설정을 받아 허용 여부를 돌려준다(테스트 모드면 항상 허용).

막힌 수신자:

- 팝빌로 넘기지 않는다. 그 수신자만 실패로 기록하고 사유 코드는 `RECIPIENT_NOT_ALLOWED`, 포인트는 차감하지 않는다. 나머지 수신자는 정상 접수한다.
- 전원이 막히면 그 발송 건은 실패로 끝나고 예약 포인트가 해제된다(기존 전원 실패 경로).
- 재시도하지 않는다(`lib/messaging/dispatch.ts`의 `NON_RETRYABLE_SUBMIT_CODES`에 추가).
- 실패 사유를 사람이 읽는 문구로 보여 주는 곳에서는 '발송 제한 번호'로 표시한다.

거르는 위치:

1. 수신자별 상태를 다루는 발송 단계: 즉시·예약이 함께 쓰는 배치 접수(`lib/messaging/dispatch.ts`)와 팩스 라우트(`app/api/bill/fax/send/route.ts`).
2. 팝빌 호출 함수(`lib/popbill/messages.ts`·`lib/popbill/fax.ts`): SDK를 부르기 직전에 한 번 더 확인한다. 목록 밖 번호가 하나라도 있으면 SDK를 부르지 않고 `PopbillSubmitError`(코드 `RECIPIENT_NOT_ALLOWED`)를 던진다. 조직 규칙을 적용하도록 접수 호출에 조직 id를 넘긴다. 새 발송 경로가 생겨도 목록 밖 번호는 팝빌로 나가지 않는다.

### 4.2 발송 결과 확정

#### ① 결과 재조회 크론

- EventBridge Rule(rate 1분) → API destination `POST /api/delivery/reconcile`. Connection은 예약 발송의 `home-erp-scheduled-messaging`을 재사용하고, IAM 역할은 이 destination 전용으로 둔다(감사 로그 purge와 같은 방식).
- 먼저 규칙이 이미 있는지 확인한다. 없으면 5절 3c 단계(배포본 운영 전환)에서 만든다.
- 만든 리소스를 `docs/ops/eventbridge-scheduled-messaging.md` 7절에 기록한다.

#### ② 발송 환경 표시

로컬과 배포본이 같은 DB를 쓰므로, 한 환경에서 접수한 작업을 다른 환경의 재조회가 엉뚱한 팝빌 서버에 조회하는 일을 막는다.

- `provider_dispatch_jobs`에 `provider_env`(`'test' | 'live'`, not null, check)를 추가한다. 기존 행은 전부 `'test'`로 채운다(운영 환경은 지금까지 열린 적이 없다 — 2절 조회).
- 작업을 만들 때 그 접수에 쓴 설정의 `isTest`로 `'test'`/`'live'`를 기록한다.
- 재조회(`claim_provider_dispatch_jobs`)는 호출한 쪽 환경과 같은 작업만 가져온다.
- RPC에 인자를 더할 때는 기본값을 둬서 마이그레이션 적용부터 배포까지의 공백에도 옛 클라이언트가 깨지지 않게 한다. 옛 시그니처는 drop해서 오버로드를 남기지 않는다. 재조회 claim의 환경 인자는 생략하면 `test`다(옛 클라이언트는 테스트 모드뿐).
- 재시도(replay) 보호: 예약에 작업이 이미 있으면 처음 만든 작업 구성이 기준이다. 허용 목록·환경이 바뀐 뒤 같은 예약을 다시 처리해도 새 작업·수신자를 더하지 않는다(2026-10-02 리뷰 반영 — 접수된 작업에 수신자가 덧붙어 결과가 확정되지 않던 문제).

#### ③ 매월 반복 예약

- 현재: 운영 결과 확정 경로인 `settle_message_points_from_jobs`는 `message_schedules.status`를 sent/partial로 바꾸지만 다음 회차를 만들지 않는다. 다음 회차 생성(`enqueue_next_message_occurrence`)은 `complete_message_schedule`에만 있다.
- 변경: 어느 경로로 확정되든 반복 예약이 sent 또는 partial이 되면 다음 회차를 만든다. `enqueue_next_message_occurrence`는 같은 회차가 이미 있으면 그 id를 돌려주므로 두 경로가 겹쳐도 1건만 생긴다.
- 전원 실패(failed)면 다음 회차를 만들지 않는다(2026-09-09 결정 유지).

#### ④ 팝빌 잔액 부족

- 팝빌 오류코드표(https://developers.popbill.com/error-code, 2026-10-02 확인)의 잔액 부족 코드 `-99005001 파트너 잔여포인트가 부족합니다.`, `-99005003 차감할 충전포인트가 부족합니다.`, `-99005004 차감할 보너스포인트가 부족합니다.`, `-99005005 잔여포인트가 부족합니다.`를 앱 코드 `PROVIDER_INSUFFICIENT_BALANCE`로 묶는다.
- 재시도하지 않는 오류에 위 4개와 `-99005002`·`-99005013`(후불 한도 초과), `-10010039`(허용되지 않은 IP)를 더한다.
- 즉시 발송 결과 안내(메신저·공지 알림톡 발송)에 "팝빌 충전 잔액이 부족해 발송하지 못했어요. 운영사에 충전을 요청해 주세요."를 보여 준다. 발송 내역·상세에는 실패 사유 칸이 없어(정본에도 없음) 이번엔 넣지 않는다.
- 조직 포인트는 실패 시 차감하지 않는다(현행).

### 4.3 발신번호 표시

- 서버가 기본 발신번호(문자 `POPBILL_SMS_SENDER`, 팩스 `POPBILL_FAX_SENDER`, 숫자)를 돌려주는 조회를 추가한다. 로그인한 직원(org 컨텍스트)만 호출할 수 있다. 화면은 React Query 훅 하나로 읽는다.
- 표시 순서: 조직 번호(`setup_config.sms_sender`·`fax_sender`) → 기본 번호 → '발신번호 미등록'.
- 적용 위치:
  - 발송 내역(`HistoryTab`)·예약(`ScheduledTab`)·발송 상세(`MessageDetailModal`): 공용 `senderLabel`.
  - 메신저 발신번호 선택(`components/messenger/SenderSelect.tsx`): '운영사 기본번호' 글자 자리에 실제 번호를 보여 주고 '기본' 배지는 유지한다. 발송 확인창(`SendSummaryDialog.tsx`)도 같은 번호를 쓴다.
  - 팩스 확인 모달(`DocumentOutputModal` → `FaxConfirmationModal`): 지금 고정 문구 → 실제 팩스 발신번호.
- 알림톡은 '관리비서 채널' 그대로 둔다(2026-09-22 결정).

### 4.4 데모 데이터 정리

- 배포본 허용 목록을 `*`로 열기 직전에 데모 조직의 남은 예약(status `scheduled`, 미래 예약·매월 반복)을 취소한다. 허용 목록 기간에는 막혀서 실패로만 끝나지만, `*`로 열면 더미 번호로 실제 발송된다.
- 테스트 시절 접수 작업에 묶인 포인트 예약은 그대로 둔다. ②로 운영 재조회 대상이 아니다.

## 5. 운영 전환 절차

1. **팝빌 쪽(대표님)**: 부록 A를 요청한다.
2. **우리 쪽 구현**: 4절 구현 → master 병합 → Amplify 배포. 테스트 모드에서는 4.1이 꺼져 있고 나머지도 동작이 같아서 운영 키보다 먼저 배포해도 된다.
3. **운영 키 도착 후 시험 발송(배포본)**
   - a. 조회 점검을 다시 돌린다(운영 가입, 발신번호 state, 잔액).
   - b. (선택) 충전 전 잔액 0 상태에서 허용 번호로 1건 보내 `-99005005`가 오는지 확인한다(접수 거절이라 과금 없음).
   - c. ## 7. 범위 밖·알려진 한계

- 알림톡 실발송: 카카오 채널 승인·템플릿 코드 대기.
- 발송 기록에 실제로 쓴 발신번호가 저장되지 않는다. 조직 번호를 바꾸면 과거 내역도 새 번호로 보인다.
- [팝빌에서 관리] 인가 범위(D3, 유지).
- 로컬 개발과 배포본이 같은 DB를 쓴다. 출시 뒤 분리는 별도 과제.
- 팩스 결과 506·517은 팝빌이 과금하는 '확인불가'다. 현재 정규화는 성공 페이지 수로만 판정해 이 경우 실패로 집계될 수 있다(실발송에서 확인).
- 팝빌 실제 잔액의 화면 표시(PRD messaging의 잔여 포인트 조회 항목)는 하지 않는다. 팝빌 사이트의 잔여 포인트 알림으로 대신한다.
- 고객 조직별 발신번호는 발신번호 개수 제한(사업자 유선 1개)에 걸려 회선 추가 신청이 필요할 수 있다. 고객 온보딩 전에 팝빌 답변으로 정한다.
- API 전송 일 단위 관리자 승인 방식에 따라 예약 발송 운영 방식이 바뀔 수 있다. 팝빌 답변을 받은 뒤 정한다.
