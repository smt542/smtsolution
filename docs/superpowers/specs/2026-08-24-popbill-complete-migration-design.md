# 팝빌 통합 발송 완전 전환 설계

> 상태: 사용자 승인 완료
> 작성일: 2026-08-24
> 범위: NCP 메시징 제거, 팝빌 SMS/LMS·알림톡·팩스 통합, 비동기 결과 정산

## 1. 배경과 목표

현재 ERP는 운영사 공용 NCP 자격증명으로 모든 관리업체의 SMS·알림톡을 발송하고, 관리업체별 포인트 예약·차감 및 월 청구를 내부에서 처리한다. 팩스는 실제 공급자 호출 없이 성공으로 기록하는 스텁이다.

운영 편의와 고객의 총비용을 기준으로 외부 발송 공급자를 팝빌 하나로 통일한다. 기존 중앙 과금, 권한, 발송 화면은 유지하되 외부 발송과 결과 확인을 팝빌 기준으로 다시 구성한다. 팝빌 접수 성공을 실제 발송 성공으로 간주하지 않고 최종 수신 결과가 확인된 항목만 정산한다.

## 2. 확정 범위

### 포함

- NCP SMS·알림톡 코드, 테스트, 환경변수 참조 제거
- 팝빌 공통 인증과 SMS/LMS·알림톡·팩스 서버 어댑터
- 팝빌 접수번호와 수신자별 결과를 저장하는 발송 작업 모델
- 즉시 발송과 예약 발송의 비동기 결과 조회 및 최종 정산
- 고지서 A4 PDF 서버 생성과 실제 팩스 발송
- SMS, LMS, 알림톡, 팩스 성공 페이지별 포인트·월 청구 집계
- 팩스 실패 세대 재발송과 발송 이력
- 운영 설정, 오류 처리, 자동 테스트, 운영 문서

### 제외

- 팝빌 외 공급자 예비 전환 또는 NCP 폴백
- 알림톡 실패 시 문자 자동 대체 발송
- 카카오 주민 로그인 스텁의 실제 OAuth 전환
- 기존 확정 월 청구서의 과거 사용량 재계산
- 광고성 친구톡·브랜드 메시지

## 3. 운영 계정과 외부 준비사항

운영사는 하나의 팝빌 파트너 계정으로 발송비를 부담하고, ERP가 관리업체별 포인트와 월 청구를 관리한다. 실제 운영 전 다음 준비를 완료해야 한다.

1. 팝빌 연동 신청과 운영사 파트너과금 계약 확인
2. 운영사 사업자번호, 팝빌 사용자 ID, API 연동 키 발급
3. 문자·알림톡 발신번호와 팩스 발신번호 등록 및 승인
4. 카카오비즈니스 통합가입과 비즈니스 채널 개설
5. 해당 채널을 팝빌에 등록하고 관리비·연체·공지 등 알림톡 템플릿 승인

팝빌은 카카오 메시지 발송 대행사이므로 카카오비즈니스 채널을 대체하지 않는다. 카카오 공식 절차에서 비즈니스 채널을 만든 뒤 팝빌에 등록해야 한다. 맞춤 알림톡은 카카오 승인을 받은 템플릿으로만 발송한다.

- 팝빌 채널 등록: <https://developers.popbill.com/guide/kakaotalk/vb/introduction/manage-channel>
- 팝빌 알림톡 템플릿: <https://developers.popbill.com/guide/kakaotalk/introduction/regist-atstemplate>
- 팝빌 알림톡 결과 확인: <https://developers.popbill.com/guide/kakaotalk/introduction/ats>

카카오 주민 로그인은 별도 Kakao Developers 앱이 필요한 독립 기능이며 이번 전환에 포함하지 않는다.

## 4. 아키텍처

### 4.1 공급자 계층

`lib/messaging`의 소비자는 공급자 중립 인터페이스만 사용한다.

- 팝빌 공통 설정: 서버 환경변수 검증, 테스트/운영 구분, SDK 초기화
- 메시지 어댑터: SMS/LMS 일괄 접수, 알림톡 일괄 접수, 결과 조회
- 팩스 어댑터: 바이너리 PDF 접수, 결과 조회
- 결과 정규화: 팝빌 코드와 상태를 ERP의 `pending`, `success`, `failed`, `reconcile_required`로 변환

공급자 자격증명이 없으면 실제 발송 경로는 명시적으로 실패한다. 운영 화면에서 성공처럼 보이는 암묵적 스텁은 제거하고, 테스트는 모킹된 어댑터만 사용한다.

### 4.2 메시지 상품 구분

사용자 화면의 문자 작성 모드는 유지하지만 정산 상품은 다음처럼 구분한다.

- `sms`: 렌더링된 최종 본문이 SMS 한도 이내
- `lms`: 최종 본문이 SMS 한도를 초과
- `alimtalk`: 승인된 카카오 템플릿과 일치하는 알림톡

수신자별 변수 치환 후 실제 바이트 길이로 SMS/LMS를 결정한다. 견적, 예약, 최종 정산 모두 같은 판정 함수를 사용하여 견적과 원가가 어긋나지 않게 한다.

### 4.3 팩스 문서 생성

서버 전용 PDF 렌더러가 기존 고지서와 동일한 데이터 계약으로 세대별 A4 PDF를 만든다. 한글 폰트는 재배포 가능한 라이선스와 함께 애플리케이션에 포함한다. PDF와 QR 이미지는 메모리 버퍼로 생성해 팝빌에 전달하고 애플리케이션 저장소나 DB에 영구 보관하지 않는다.

세대별 문서와 번호가 다르므로 팩스는 세대별 독립 작업으로 접수한다. 접수번호, 상태, 성공·실패 페이지 수, 오류 코드만 저장한다.

## 5. 데이터 모델

### 5.1 공급자 발송 작업

새 발송 작업 테이블은 다음 정보를 보관한다.

- 관리업체, 공급자(`popbill`), 종류(`message` 또는 `fax`), 상품
- 메시지 포인트 예약 또는 고지서 발행 건과의 연결
- ERP 고유 요청번호와 팝빌 접수번호
- `submitting`, `pending`, `sent`, `partial`, `failed`, `reconcile_required` 상태
- 수신자 키와 팝빌 수신자 식별자의 매핑
- 결과 조회 시각, 다음 조회 시각, 재시도 횟수, 정제된 오류
- 팩스 총 페이지, 성공 페이지, 실패 페이지
- 생성·완료 시각

ERP 고유 요청번호는 유일해야 한다. 메시지 자동 모드가 여러 상품으로 나뉘면 하나의 포인트 예약에 여러 발송 작업이 연결될 수 있다. 기존 단일 `provider_request_id`는 호환 목적으로 남길 수 있지만 새 작업 테이블을 발송 식별자의 기준으로 사용한다.

### 5.2 포인트 예약 상태

팝빌이 접수를 수락하면 포인트 예약을 `provider_pending`으로 전환한다. 이 상태의 금액은 가용 포인트에서 계속 제외하며 15분 만료만으로 수동 해제할 수 없다.

최종 결과가 확인되면 수신자별 실제 성공 상품을 기준으로 정산한다.

- 전부 성공: 성공분 차감 후 `settled`
- 일부 성공: 성공분만 차감하고 나머지 반환 후 `settled`, 로그는 `partial`
- 전부 실패: 전액 반환 후 `released`
- 결과 확인 불가: 금액을 유지하고 `reconcile_required`

팝빌 접수가 확인된 작업은 운영자가 공급자 결과를 확인하지 않고 단순 해제할 수 없게 한다.

### 5.3 SMS/LMS와 팩스 청구

메시지 포인트 단가와 플랫폼 원화 단가에 `lms`를 추가한다. 견적 카드와 관리 화면은 SMS와 LMS 건수·단가를 각각 표시한다.

팩스 월 사용량은 발송 요청 건수가 아니라 팝빌이 반환한 실제 성공 페이지 합계로 집계한다. 새 청구 규칙은 마이그레이션 적용 이후 발송분부터 사용하며 이미 확정된 과거 청구서는 변경하지 않는다.

팩스 재발송은 append-only 이력으로 남긴다. 재발송으로 실제 성공한 페이지도 팝빌 원가와 동일하게 월 사용량에 포함한다.

## 6. 메시지 발송 흐름

1. 사용자 권한, 관리업체, 템플릿, 수신자 동의를 검증한다.
2. 수신자별 본문을 렌더링하고 SMS/LMS/알림톡 상품을 확정한다.
3. 현재 단가로 견적을 다시 계산하고 배치 전체 포인트를 예약한다.
4. 상품별 수신자를 팝빌 일괄 API에 접수한다.
5. 고유 요청번호와 팝빌 접수번호를 저장하고 예약을 `provider_pending`으로 바꾼다.
6. API는 `queued`와 접수된 수신자 수를 반환한다. 아직 성공 토스트나 확정 차감을 표시하지 않는다.
7. 결과 조회 작업이 각 수신자의 최종 결과를 정규화한다.
8. 모든 수신자가 최종 상태가 되면 한 번만 포인트를 정산하고 메시지 로그를 갱신한다.
9. 예약 발송은 동일한 흐름을 사용하며 최종 결과 확인 후 스케줄을 완료한다.

접수 호출 전에 확정적으로 실패하면 포인트를 전액 반환한다. 타임아웃처럼 접수 여부가 불분명하면 같은 내용을 즉시 재전송하지 않고 고유 요청번호 또는 접수번호로 먼저 조회한다.

## 7. 팩스 발송 흐름

1. 서버 Route Handler가 로그인, `bill_publish` 권한, 관리업체와 건물 소유권을 검증한다.
2. 확정된 관리비와 현재 수신 팩스번호를 서버에서 다시 조회한다.
3. 세대별 A4 PDF를 만들고 팝빌 바이너리 팩스 API에 접수한다.
4. 각 세대의 고유 요청번호와 접수번호를 저장하고 고지서 상태를 `queued`로 표시한다.
5. 결과 조회 작업이 성공·실패 페이지와 오류를 반영한다.
6. 실제 성공 페이지가 있는 경우에만 `sent` 또는 `partial`로 표시하고 월 팩스 사용량에 반영한다.
7. 실패 세대는 화면에서 선택해 새 시도로 재발송할 수 있으며 이전 시도는 보존한다.

## 8. 결과 조회와 오류 처리

기존 예약 발송용 `CRON_SECRET` 보호 방식을 재사용한 공급자 결과 조회 엔드포인트를 둔다. DB claim RPC가 처리 대상을 임대하고 `FOR UPDATE SKIP LOCKED` 방식으로 중복 작업을 방지한다. 팝빌이 공식 지원하는 API Polling을 최종 상태의 기준으로 사용한다.

조회 간격은 처음 10분 동안 1분, 2시간까지 5분, 24시간까지 30분으로 늘린다. 24시간 후에도 최종 결과가 없으면 자동 실패나 환불을 하지 않고 `reconcile_required`로 전환한다.

오류 응답에는 팝빌 비밀키, 전체 공급자 응답, 수신자 개인정보를 포함하지 않는다. 저장하는 공급자 결과도 정산과 지원에 필요한 코드·상태·페이지 수로 제한한다.

알림톡 실패 후 팝빌 대체문자 옵션은 사용하지 않는다. 대체문자는 SMS/LMS 별도 과금과 중복 정산 가능성이 있으므로 추후 명시적 사용자 선택, 별도 견적, 별도 결과 매핑 설계가 있을 때 추가한다.

## 9. 환경 설정

운영 환경은 다음 종류의 서버 전용 값을 요구한다.

- 팝빌 Link ID와 Secret Key
- 운영사 사업자번호와 팝빌 사용자 ID
- 테스트/운영 환경 플래그
- 등록 완료된 문자·알림톡·팩스 발신번호
- 기존 예약 발송 및 결과 조회용 `CRON_SECRET`

구체적인 환경변수 이름은 `POPBILL_` 접두사로 통일하고 필수값을 한 곳에서 검증한다. NCP 환경변수는 코드와 배포 문서에서 제거한다. 실제 비밀값은 저장소에 커밋하지 않는다.

## 10. 테스트와 검증

### 자동 테스트

- 설정 검증과 테스트/운영 분리
- SMS/LMS 바이트 판정과 수신자별 변수 치환 후 견적
- 메시지·알림톡·팩스 요청 매핑과 공급자 응답 정규화
- 미인증·권한 없음·다른 관리업체 데이터 접근 차단
- 접수 실패, 접수 여부 불명, 부분 성공, 전부 실패
- 결과 조회 중복 실행과 정산 멱등성
- `provider_pending` 포인트의 가용 잔액 제외 및 무단 해제 차단
- 예약 발송의 접수·대기·최종 완료 전이
- A4 PDF 생성, 한글 렌더링, 세대별 팩스 작업 생성
- 팩스 성공 페이지 월 청구와 실패 세대 재발송 이력
- NCP 코드와 환경변수 참조 부재

### 저장소 검증

- 관련 Vitest와 전체 테스트
- TypeScript 타입 검사
- ESLint
- Next.js 프로덕션 빌드
- Supabase 마이그레이션 검증 SQL

### 실제 운영 검증

팝빌 테스트 자격증명으로 SMS, LMS, 알림톡, 팩스를 각각 접수하고 결과 조회까지 확인한다. 운영 전환 후에는 승인된 발신번호와 알림톡 템플릿으로 소수 내부 번호에 카나리 발송한다. 자격증명이 제공되지 않은 상태에서는 자동 테스트와 어댑터 계약까지만 완료로 판단하며 실제 발송 성공을 주장하지 않는다.

## 11. 수용 기준

1. 코드와 배포 설정 문서에 NCP 발송 의존성이 남지 않는다.
2. SMS, LMS, 알림톡, 팩스가 팝빌 접수번호를 생성하고 결과 조회 대상이 된다.
3. 접수만 된 건은 성공 또는 확정 차감으로 표시되지 않는다.
4. 실제 성공 수신자와 성공 팩스 페이지만 포인트·월 청구에 반영된다.
5. 중복 API 호출과 중복 결과 조회가 중복 발송·차감을 만들지 않는다.
6. 팩스 PDF가 서버에서 생성되고 개인정보 문서가 애플리케이션 저장소에 남지 않는다.
7. 관리업체별 권한, 포인트, 월 청구 경계가 유지된다.
8. 공급자 미설정 시 가짜 성공 대신 명확한 설정 오류가 반환된다.
9. 자동 테스트, 타입 검사, 린트, 프로덕션 빌드, SQL 검증이 통과한다.
