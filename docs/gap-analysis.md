# 주택관리ERP — 명세↔구현 갭 분석

> **작성일** 2026-08-14 · **기준 커밋** `8acfb5d`(origin/master 최신화 후)
> **범위** 구현이 존재하는 **staff + admin** 화면. partner(10)·resident(14)는 라우트 자체가 없어 전체 미구현(§8).
> **⚠️ 정정 이력** 최초 분석은 **로컬 master가 41커밋 뒤처진 상태**에서 수행돼 수납(payment)·고객번호조회(customer-numbers)·P5c 혼합건물을 "미구현"으로 오판했다. 최신화 후 **영향 화면(payment·customer-numbers·utilities·입주자폼·overdue)을 재검증**해 이 문서를 정정했다. 각 항목의 ✅는 "재검증에서 이미 구현 확인(오탐 해소)", ❗는 "재검증에서도 유효한 진짜 갭".
> **읽는 법** 명세가 잘게 나눈 화면을 구현이 한 라우트로 **통합**하거나 **분리**(예: 수납을 receipt-management 명세와 달리 `/staff/payment`로 분리)한 것 자체는 갭이 아님(구조 설계). 갭 = ①누락 ②동작 불일치 ③명세 밖 초과 ④통째 미구현.

## 0. 총평

구현은 예상보다 **훨씬 진척**돼 있다(수납 자동이체·은행매칭·고객번호조회·공과금 단가·부과확정 등 최신 기능 다수 반영). 남은 갭은 크게 **(A) 계산 정책 불일치(저비용·고영향)**, **(B) 데이터 연동 누락(overdue↔payments)**, **(C) 보안 경계(admin PII)**, **(D) 화면별 세부 기능 미구현**, **(E) 제품 방향 결정 필요(admin·공과금 계산 모델)** 로 나뉜다.
