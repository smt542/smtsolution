# 주택관리ERP 화면별 API 기능 체크리스트

> 기준일: 2026-09-22 KST
> 원본: 외부 WBS/Notion 워크스페이스 **주택관리ERP**를 같은 날 읽어 생성
> 목적: 화면 정책의 요구 기능을 API 계약·코드 연결·검증 증적으로 하나씩 대조하기 위한 최초 기준선

## 판정 원칙

- 이 문서는 **정책상 필요한 기능**을 정리한 것이며, 아직 구현 여부를 판정하지 않습니다. 모든 상태는 `[ ]`(미점검)으로 시작합니다.
- `API 계약`은 실제 Route Handler·Supabase RPC·PostgREST·Storage·외부 제공자 호출 중 어떤 경계인지, 요청/응답/오류 계약이 확인됐을 때만 완료 처리합니다.
- `코드 연결`은 호출 코드와 서버/RPC 구현, 권한·조직 범위 검증까지 연결된 증적이 있을 때 완료 처리합니다.
- `검증`은 정상·오류·경계·권한/테넌트 격리 케이스의 자동 또는 재현 가능한 수동 테스트 증적이 있을 때 완료 처리합니다.
- 문서에 나온 연동 키워드는 **후보**일 뿐 확정 endpoint/RPC 이름이 아닙니다. 코드 대조 후 실제 이름으로 갱신합니다.

## API 계약 공통 체크

각 기능 행의 `API 계약`을 완료하기 전 아래 항목을 확인합니다.

- [ ] 기능 ID와 책임(조회/변경/인증/외부연동)을 확정했다.
- [ ] 실제 인터페이스 종류와 이름(Route, RPC, PostgREST, Storage, 외부 SDK)을 기록했다.
- [ ] 입력 필수값·형식·범위·페이지네이션/정렬·멱등키 여부를 기록했다.
- [ ] 응답 모델과 빈 결과·부분 성공·오류 코드를 기록했다.
- [ ] persona·모듈 권한·조직/건물/세대 범위·RLS를 확인했다.
- [ ] 상태 전이, 중복 방지, 감사로그/접근로그, 개인정보 마스킹 필요 여부를 확인했다.
- [ ] 로딩·빈 상태·성공·에러·재시도 UI 동작을 정책과 대조했다.

## 범위·문서 커버리지

원본 WBS에는 총 70개 문서가 있으며, 공통 정책 9개·회의록 3개·화면 문서 58개로 구성되어 있습니다. 화면 지도는 62개 정식 화면을 정의합니다.

- 현재 체크리스트는 최신 통합 입주자 정책서를 포함해 **56개 정책 패키지, 정식 화면 57개**를 다룹니다.
- 별도 정책 문서가 없는 정식 화면 **5개**는 아래 선행 보완 대상으로 분리했습니다.
- 기존 `사무실 관리자_입주자 상세`, `사무실 관리자_입주민 등록` 문서는 `입주자 상세·등록 정책서 (UI중심)`이 두 화면을 통합해 대체하므로 중복 점검 대상에서 제외했습니다.

## 점검 진행 규칙

1. 표의 기능 ID별로 실제 훅·Route·RPC·마이그레이션을 찾아 API 계약을 채웁니다.
2. 구현 위치와 권한/데이터 범위 증적을 남긴 뒤 `코드 연결`을 완료 처리합니다.
3. 정상·실패·권한 거부·타 조직/중복/경계값을 검증한 뒤 `검증`을 완료 처리합니다.
4. 문서가 없거나 정책이 모호한 항목은 구현 결함으로 단정하지 않고 **정책 결정 필요**로 기록합니다.

## 공통 흐름·교차 화면 점검

화면별 기능을 점검할 때 아래 업무 흐름의 앞뒤 API 계약도 함께 대조합니다.

- [ ] 건물 등록 → 입주자 등록 → 검침/지침 입력 → 관리비 부과 설정 → 부과 확정 → 고지서 발행/발송 → 수납 → 미납 관리 → 이사정산의 상태·참조 무결성
- [ ] staff ↔ partner: 현장 검침·A/S·이사정산 입력이 사무실 데이터와 같은 조직·건물·세대 범위로 연결되는지
- [ ] staff ↔ resident: 공지, 고지서/서명 링크, 세대연결 요청과 승인 흐름의 권한·만료·개인정보 보호
- [ ] admin ↔ tenant: 본사는 운영 메타데이터만 직접 열람하고, 테넌트 업무 데이터 접근은 정책상 분리되는지
- [ ] 문자·알림톡·팩스·은행/CMS·엑셀 등 외부 연동은 멱등성, 부분 성공, 재시도, 포인트/정산, 감사 증적을 남기는지
- [ ] 변경성 기능은 감사로그, 개인정보 원문·반출·출력·발송은 접근로그 및 마스킹 정책을 충족하는지
